# Deployment

## Environment variables

### Backend (`backend/.env`)

| Variable | Default | Notes |
| --- | --- | --- |
| `PORT` | `4000` | |
| `NODE_ENV` | `development` | Set to `production` to hide error details |
| `JWT_SECRET` | dev value | **Must be changed.** A long random string |
| `JWT_EXPIRES_IN` | `12h` | One working day |
| `DATABASE_URL` | — | Postgres connection string. Blank runs PGlite in process, out of `PG_DATA_DIR` — no server to install. |
| `PG_DATA_DIR` | `./data/pg` | Where PGlite keeps its data when `DATABASE_URL` is blank |
| `CORS_ORIGINS` | localhost list | Comma-separated; set to your real web domain |
| `OTP_DEV_MODE` | `true` | **Set to `false` in production** — otherwise every code is `123456` |
| `SHOP_NAME`, `CURRENCY` | Al Hadeed Hardware, UGX | Shown on receipts |
| `ADMIN_NAME`, `ADMIN_PHONE`, `ADMIN_PASSWORD` | — | Used once by `db:bootstrap` to create the first manager on an empty database. Remove the password afterwards. |
| `SMS_PROVIDER` | `log` | `log` (console only), `africastalking`, or `generic` with `SMS_URL` |
| `SMS_API_KEY`, `SMS_USERNAME`, `SMS_SENDER_ID` | — | Gateway credentials, for login codes and order confirmations |

## Before going live

1. **Set `JWT_SECRET`** to a long random value. Anyone who knows it can forge a
   manager token.
2. **Set `OTP_DEV_MODE=false`** and connect an SMS gateway — see below. Left on,
   anyone can sign in as any customer with `123456`.
3. **Change every seeded staff password.** The demo passwords are in this repo.
4. **Serve over HTTPS.** Tokens travel in the `Authorization` header.
5. **Lock `CORS_ORIGINS`** to the real web panel domain.
6. **Back up the database file** on a schedule — it holds the cash book.

### Connecting an SMS gateway

The OTP is generated in `POST /api/auth/otp/request` in
[backend/src/routes/auth.js](../backend/src/routes/auth.js). The code is already
stored and expiring correctly; the only missing piece is the send. Replace the
comment marked `// In production this is where the SMS gateway is called` with
your provider's call, and stop returning `devCode`.

| Piece | Where | Why |

| Web panel | Vercel | Plain Next.js. Root directory `web`. |
| Mobile | `eas build` for the Play Store and App Store | |
| Domain / CDN | Namecheap + Cloudflare | Proxy the panel; the API needs WebSocket support enabled. |

## Step by step: the API on Render

[`render.yaml`](../render.yaml) in the repository root is a Render
Blueprint — it declares the service, the Node version, the disk, the health
check and every environment variable, so most of this is already done.

**1.** On render.com: **New → Blueprint** → pick this repository → **Apply**.

**2.** Render asks for the values the blueprint marks `sync: false`. Everything it provisions is on the free tier:

| Variable | What to put |
| --- | --- |
| `CORS_ORIGINS` | The Vercel domain, e.g. `https://alhaheed-hardware.vercel.app`. Put `http://localhost:3000` for now and correct it in step 7. |
| `ADMIN_NAME` | The first manager's name |
| `ADMIN_PHONE` | Their phone, any format — `0704892253` is fine |
| `ADMIN_PASSWORD` | At least 8 characters. Used once. |
| `SMS_USERNAME`, `SMS_API_KEY`, `SMS_SENDER_ID` | From your Africa's Talking account. For a first smoke test set `SMS_PROVIDER=log` instead and read the codes in the service log. |

`JWT_SECRET` is generated by Render and never leaves it.

**3.** Apply. On first boot `npm run db:bootstrap` creates the tables, one
manager account and the seven product categories. It loads **no demo
accounts** — the `cashier123` logins in the README exist only in local
development.

If `ADMIN_PHONE` or `ADMIN_PASSWORD` is missing the deploy fails on
purpose, with the reason in the log. A shop nobody can sign in to is not a
successful deploy.

**4.** Check `https://<your-service>.onrender.com/api/health` →
`{"ok":true,...}`.

**5.** Sign in as the manager and add the real staff and products. Then
**delete `ADMIN_PASSWORD`** from the Render environment; it is never read
again once a staff account exists.

### The database comes with it

The blueprint declares a PostgreSQL alongside the API, so Render creates
both and injects the connection string. There is nothing to copy, nothing
to paste, and no second account anywhere:

```yaml
databases:
  - name: alhadeed-db
    plan: free

    # …and in the service:
    - key: DATABASE_URL
      fromDatabase:
        name: alhadeed-db
        property: connectionString
```

A database rather than a file on disk because a free Render service has
no persistent disk: a file inside the container is wiped on every deploy,
restart and wake from sleep. The database is a separate thing and
survives all of it.

### Two things about the free tier

**Render's free PostgreSQL expires.** It runs for a limited period and is
then deleted — check their current terms rather than trusting a number
written here. Before that day, either upgrade the database to a paid
instance or move it. Any ordinary PostgreSQL works; change
`DATABASE_URL` and nothing else:

```bash
pg_dump "$OLD_DATABASE_URL" > alhadeed.sql
psql "$NEW_DATABASE_URL" < alhadeed.sql
```

Worth putting that `pg_dump` in the calendar regardless. A shop's order
history is not something to hold in one copy.

**The free web service sleeps** after about 15 minutes without traffic.
The first request afterwards takes the best part of a minute, and the
Socket.IO connection drops, so the cashier's screen stops updating live
until someone reloads. Orders and money are safe; the screen just needs a
refresh after a quiet spell. A paid instance removes it.

## Step by step: the panel on Vercel

**6.** **New Project** → import this repository → **Root Directory: `web`**
(not the repository root, and not `backend`). Next.js is detected; leave
the build and output settings alone.

Add one environment variable before deploying — it is read at build time,
so setting it afterwards means a redeploy:

```
NEXT_PUBLIC_API_URL = https://<your-service>.onrender.com
```

No trailing slash.

**7.** Copy the Vercel domain, go back to Render, and set `CORS_ORIGINS` to
it. Until this is right the browser blocks every API call and sign-in fails
with *"Can't reach the shop"* even though both halves are running.

**8.** Open the Vercel URL and sign in. If the payment queue loads, the
chain works end to end.

Remember the panel is the **Cashier and Accounts desks only**. Customers,
the Store Manager and the Manager are on the phone.

## Running the API anywhere else

`npm start` in `backend/` is the entry point; it needs **Node 20 or
newer** and a `DATABASE_URL`. Run `npm run db:bootstrap` before it — the command is safe to repeat and does nothing once the shop
has data. Put it behind a process manager (`pm2` or a systemd unit) so it
comes back after a reboot, and make sure the reverse proxy passes
WebSocket upgrades through or real-time order hand-off will not work.

## About the database

PostgreSQL, through one module: [`backend/src/db/index.js`](../backend/src/db/index.js).

| `DATABASE_URL` | What runs | Used for |
| --- | --- | --- |
| set | `pg`, against a real server | production |
| unset | PGlite — PostgreSQL compiled to WebAssembly, in process, writing to `PG_DATA_DIR` | local development and the test suite |

Both are the same engine, so there is no dialect gap between what the
tests prove and what the shop runs.

Two details worth knowing before changing the schema:

- **Timestamps are `TEXT`**, holding `'YYYY-MM-DD HH:MM:SS'`, written by
  the `now_text()` function in `schema.sql`. Every client reads them as
  strings; a `timestamptz` comes back from the driver as a Date, becomes
  ISO with a T and a Z, and breaks the web panel's formatting and the
  Flutter app's time slicing alike.
- **Money is `INTEGER`**, in whole shillings. UGX has no sub-unit worth
  tracking, and integers cannot drift the way floats do.

The query helpers keep `?` placeholders and translate them to `$1, $2, …`,
and `run()` reports `lastInsertRowid` by appending `RETURNING id` to an
INSERT that has no RETURNING of its own.

## Phase 2

Not built in this MVP, and where each would go:

### Online payment in-app (Pesapal — mobile money and card)
The customer would pay before the cashier stage. Add a `payment_intents` table
and a Pesapal IPN webhook route; on a confirmed callback, create the `payments`
row exactly as the cashier does and move the order straight to `paid` (or to
`payment_verified`, if a gateway confirmation counts as verification for your
accountant). The order flow and all four desk screens stay as they are — one
more way in at step 2.

### Delivery tracking
`orders` already carries `fulfilment` and `delivery_address`, and the store
records a delivery status on release. Add a `deliveries` table (driver, vehicle,
dispatched/arrived timestamps, optionally GPS points) and a sixth step to the
customer's progress list.

### EFRIS e-receipts
URA's EFRIS needs invoice data submitted at the point of sale. The natural hook
is just after `verifyPayment()` succeeds: the payment is confirmed and the
receipt number already exists. Store the EFRIS invoice number and QR payload on
the `payments` row and render it on the receipt.
